## v0.3.0：恢复真实官网流程，重做原生界面

这轮新增要求是「541 也要解决」和「像 macOS 原生应用」。验收分开：真实官网供货可读、登录可以确认、试跑可到达正确接管点、界面可以看懂并操作。库存读取成功不能代替登录或下单成功。

- **必须：程序能读取在售商品的实际自提信息。** 正式 Chrome 采用受支持本机连接、软件独立资料目录和正常浏览器设置，已由程序读取上海附近 12 家门店；继续验证同一会话重复查询与登录。没有迁移日常浏览器 Cookie，也没有使用隐藏下单 API。
- **必须：等待正常页面状态，不能把错误当成无货。** 配送预估 GET 的 403/541 单独记录；真正库存、登录、订单变更、429 和服务器指定等待仍暂停。自提入口缺失不更新库存时间。供货弹窗的加载骨架要等标题出现后再操作。
- **必须：每次持续检测都取得新响应。** 实际地区选择器记住区县页；重查时先通过可见「省份」标签回到省份选择，随后正常选择目标区县，等浏览器新请求完成才更新时间。调整过的真实浏览器离线夹具先使旧代码失败，修复后通过；官网重复读取另行记录。
- **必须：保持同一软件会话。** 登录、商品、门店和试跑串行共用一个 Chrome 进程。正常关闭使用浏览器自身退出命令保存资料。重启后的有到期时间合成 Cookie 可恢复，Apple 实际认证有效期仍由官网决定。
- **必须：原生界面可以直接使用。** 六页侧栏、细线表单、克制蓝色和白色内容区；控制台集中显示购买计划、时间、登录和日志。已保存的颜色/容量显示中文，内部保留官网原值。默认窗口无裁切；最小窗口允许纵向滚动。
- **保留原有条件：** 单次提交锁、最终商品/总价/数量/门店/付款核对、实际二维码与订单绑定、期限到期隐藏。官网试跑不能自动提交真实订单。

完整视觉稿、实际窗口及逐项比较在 [UI_DESIGN.md](UI_DESIGN.md)。核心源码、打包和官网证据在 [VERIFICATION.md](VERIFICATION.md)。没有把首发尚未发生的拥堵、全品类适配或银行实际付款写成已通过。

| 门店时段由当前结账签发 | 后续增加日期/时段选择时只使用本次可见可选项，提交前核对；失效时段须重新读取 | 待实测；本次已付款后确定取货日期的页面不能用报告的另一条路径替代 |
| 核对页可更改门店而保留其他信息 | 下一轮验证官网“更改零售店”的正常路径，争取保留已完成的取货人、验证和付款设置 | 待实测；变更后重新核对商品、金额、门店与期数，不默认验证仍有效 |
| 订单提交不能重试 | 现有持久订单锁在超时、停止和重启后均保留，只核对结果 | 已实施并通过测试 |
| 付款信息与创建时间可关联 | 现有二维码必须与唯一可见订单号关联；已知提交时刻才计算期限。后续可验证当前页面的创建时间，解决恢复后的未知起算时刻 | 图片裁取已验证；页面模型字段尚未在本机验证，暂不靠重新打开页面延长期限 |

前一天登录与准备购买条件仍有帮助，但 Apple 账户登录、当次结账及短信验证不是同一个有效期。保持打开浏览器不能保证服务器允许旧结账跨天继续；软件在开售前复核，最终按当时官网要求处理。

Apple 官方说明支持将 iPhone 短信同步到自己的 Mac，也说明 Safari 能提供收到的安全码建议（[短信转发](https://support.apple.com/zh-cn/102545)、[Safari 安全码自动填充](https://support.apple.com/zh-cn/guide/safari/ibrwa4a6c6c6/26.0/mac/26)）。这不能证明本软件的独立 Chromium 已有同样能力；本轮不读取“信息”数据库，也没有配置验证码向服务器转发。

报告中的代理池、分布式并发、自动解站点挑战和接码平台没有加入当前单账户产品。本轮保留正常浏览器流程与官网等待要求，不根据资料批量创建订单。

### 独立思考与本机反证

没有直接把 PDF 的“UI 慢”结论改写成“需要重写全部接口”。首先检查正常供货流程是否正确，实际发现两个问题：记住门店后入口叫“Apple 南京东路”；弹窗区域按钮的名称只有“上海”，不是它旁边的说明文字。旧代码分别会等待不存在的入口，或跳过区域动作而读取旧列表。

按 2026-10-11 当前官网控件建立网络完全拦截的浏览器测试，旧实现两个场景均失败；修复后重新查询、无货变有货、拒绝时不发布旧结果、未知控件不更新检测时间均通过。新的查询不调用报告中私有接口，只点击正常区域控件并观察该动作完成的浏览器请求。无货等待也加入逐步退避，避免一直使用初始短间隔。

另外用软件本身正常显示窗口的 Chromium 做两次受控官网读取，只用公开 iPhone 17 配置，不加载身份、不加购、不进入结账。通常准备在 5.90 秒内遇到关键 fetch HTTP 541；等待页面完整加载的对比在进入供货步骤时仍遇 HTTP 541，16.89 秒结束。这个观察说明等待加载未解决拒绝；不能归因于仅使用无头浏览器，也不能依据 PDF 断言是 Cookie 或挑战的哪一个问题。对比还暴露了弹窗等待超时掩盖真实拒绝原因的问题，已修复为优先保留官网限制提示。

## 一页需求：开售前能看懂准备状态，操作失误不会破坏准备

**问题**：v0.1 的关键准备分散在六页；启动失败只提示第一个问题。“停止”关闭预登录浏览器；切换时区只改时区标签会改变实际预约时刻。访问受限后缺少清晰倒计时，多订单只能直接看最近付款码。

**目标用户**：在发售前准备自己或指定取货人的一次购买，开售时减少填表、重登录和错误恢复步骤的人。

**用户流程**：准备检查 → 定位缺失设置 → 官网在售试跑 → 保持软件浏览器登录 → 设定准确开售时刻 → 开售检测 → 官网最终核对 → 订单对应付款码交接。

| ID | 优先级 | 需求与验收条件 |
|---|---|---|
| FR-01 | Must | “停止任务”结束当前操作并保留同一浏览器、会话 Cookie 与进程锁；“关闭会话”或退出应用才关闭浏览器。提交结果不明仍保留订单锁 |
| FR-02 | Must | 柏林 14:00 切换北京时间显示 20:00，实际时刻不变；显示两地时间。过去的预约阻止新真实任务；夏令时歧义须重新明确设置。旧订单仍允许核对 |
| FR-03 | Must | 清单同时列出商品、预算、门店、身份授权、付款、时间、环境、登录和已有订单。每个缺失项可定位设置；官网试跑允许人工填身份，不因此阻塞 |
| FR-04 | Should | 官网受限后显示等待秒数，期限内禁用继续；停止后启动另一个浏览器命令仍须等待，不通过重开任务跳过等待 |
| FR-05 | Should | 门店结果显示检测时间。按商品 URL、配置、数量分开记录变化，相同结果不重复记录。记录只来自实际读取 |
| FR-06 | Should | 可从订单列表选择对应付款码，不把最近付款码当作所选订单的码。重新打开不延长期限；订单列表不把已创建误报为已付款 |
| FR-07 | Must | 活跃任务使用启动时配置副本；界面后续修改不能改变正在执行的购买条件 |
| FR-08 | Must | 通用入口和已记住的门店入口都可识别；查询必须重新触发正常区域动作并等请求和新列表完成。旧 DOM 重读、错误响应和未知控件不能更新检测时间 |
| FR-09 | Should | 无货期间同一浏览器只查询供货，不反复结账；等待逐步增长到配置上限，收到关键拒绝时暂停。弹窗未打开时发生拒绝也保留真实限制原因 |
| FR-10 | Must | 鼠标、macOS 辅助功能和准备清单跳转均保持侧栏选择与实际页面一致，不出现“运行记录”选中但仍显示商品设置的状态 |
| FR-11 | Must | 登录返回还在加载时最多观察 15 秒，显示“暂时无法确认”；关键后台登录请求被拒绝时立即显示 HTTP 原因并保留会话，不自动再次提交密码 |
| FR-12 | Should | 使用紧凑浅色 macOS 工具布局，保留原有六页。默认窗口同时显示预约、登录、状态和日志；减少大卡片、数字导航及装饰文案，诊断功能按需打开 |
| FR-13 | Must | 开售时刷新已准备的目标商品页；公开导航最多等待 8 秒，不等待全部图片。第一次连接失败可正常重试；HTTP 541 的等待不会因导航超时或浏览器错误页被跳过 |

**成功标准**：以上验收场景在本机自动化测试和原生界面中通过；现有单次提交、金额/门店/分期核对及付款码到期保护保持通过。真实首发成功率、24 小时 Apple 登录寿命、桌面自动消费全流程仍待实际验证；测试通过不替代这些结果。

**本轮验证**：v0.2.1 的 105 项已通过。v0.2.2 增加登录异步返回、公开页慢资源、首次连接失败及拒绝期间不刷新验证；最终测试数、安装版和界面证据见 [验证清单](VERIFICATION.md)。

### v0.2.2 的界面与入口判断

用户明确希望界面少一些模板化观感。因此采用灰色侧栏、系统字体、普通按钮和一条紧凑状态栏；当前时钟与阶段不再占用三张大卡片。默认窗口保留足够的日志空间，环境工具与合成数据测试进入「诊断…」。新配置默认北京时间，原有预约时刻与保存设置不作隐式改动。

本机同一天对照发现：普通 Chrome 正常窗口可查到 12 家门店；正式 Chrome 的独立 Playwright 目录仍遇 541，允许正常 Service Worker 也没有恢复。公共网络诊断返回德国，但该服务的路由不能证明 Apple 请求的具体出口。现有证据不足以把故障归为“德国网站”“只有无头模式”或某一个 Cookie；仍须解决独立软件浏览器的实际兼容性。详细时刻、成功与失败的边界见 [入口研究](RESEARCH.md)。
