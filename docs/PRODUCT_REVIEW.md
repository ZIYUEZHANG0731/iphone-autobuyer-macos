# 产品需求与自我迭代

## v0.7.1：预先配置后直接执行

用户不希望再找链接、输入另一套授权密码，或在结账中重复确认已同意的隐私声明。配置流程改为选机型、颜色和容量后自动匹配官网 SKU；官网当前公开的 56 个配置链接已经随应用保存。目录更新也读取这些公开链接，缺少唯一匹配时沿用官网机型页，不要求粘贴或猜测型号。

Apple 账号密码可直接输入后本次使用，默认开启自动登录和预选信任浏览器，不触发系统安全存储。可另选持久保存；系统自身的钥匙串/凭据管理器提示和 Apple 验证码不能伪装成已经完成。打开编辑表单不再先读取旧密码，已经成功读取的账户与取货资料在本次进程中复用。

隐私确认默认自动执行，移除软件二次确认窗口和正文版本门槛。游客入口背景按钮不会因弹窗消失，因此以实际结账阶段变化推进；自动同意也覆盖此时仍位于商店登录入口的页面。自提门店匹配兼容编号前缀，仍核对官网门店编号，不将同名的其他门店当作目标。

速度改进应减少操作与等待：SKU 已选中的配置只核对、不重复点选；结账集中读取控件并在页面变化时继续。真实现货试跑、打包启动、离线回归和首发拥堵性能分别记录，前几项成功不能代替最后一项。实际结果见 [验证清单](VERIFICATION.md)。

## v0.6.0：软件沿用用户真正能登录的 Chrome

用户的日常 Chrome 已确认能登录，而恢复旧启动方式的软件独立会话仍在中国区认证提交返回 503。产品目标应当是软件能够继续这个真实会话；继续改界面名称或只观察购物袋姓名不能满足验收。

新增「接入日常 Chrome」入口，采用 Microsoft 官方 Playwright Extension，用户选择一个 Apple 中国商店页面并授权当次连接。连接过程中不复制浏览器资料、Cookie 或密码，不保存免确认令牌；关闭会话只断开软件，日常 Chrome 保留。独立 Chrome 与内嵌模式仍可选择，旧配置不会静默切换。

build 20 的真实扩展连接已经建立，但暴露了另一个软件问题：选定的受保护订单列表可正常显示，软件却另开通用账户入口，并要求可见的退出链接。build 21 改为从当前账户/订单列表，或订单详情唯一可见的官方订单列表链接，发起新的只读复核；仅接受同源的正常订单路径。订单列表必须具有实际观察到的标题和合法订单详情链接，明确登录表单优先判为失效。原页面保持，不能用缓存中的过期订单详情冒充新认证。

本轮自查的验收条件：真实扩展能连接；新请求能确认受保护页面；关闭软件连接不关闭日常 Chrome；新配置仍保留商品、门店和付款计划。扩展连接和 Apple 认证分开记录，独立会话的认证 503 不因这项替代方案宣称已修复。权限及使用方法见 [沿用日常 Chrome](DAILY_CHROME.md)，实际验收见 [验证清单](VERIFICATION.md)。

## v0.5.3：登录验收以真实会话为准

用户进一步说明日常 Chrome 的成功入口为「商店 → 购物袋 → 登录」。预登录改为完整沿用这个可见流程，登录链接及跳转上下文由官网生成；补齐没有末尾斜线的 `/shop/signIn?…` 识别。真实观察发现购物袋显示退出登录仍可能需要重新认证，所以只能把它视为记住账户：继续点击官网当次账户链接，通过受保护页面确认。已有验证码页不被覆盖；正常 Chrome 的成功结果不能代替软件自身验收。

按用户要求，预约、状态栏时钟和运行记录固定为北京时间，移除时区下拉框及第二套时间。旧预约换算后保持同一个绝对时刻，保存重读也不能改变开售时间。

检查还复现了正常关闭重开后会话 Cookie 丢失：原先只验证有有效期的 Cookie。现恢复软件 Chrome 的会话 Cookie，同时避免自动载入旧的登录、结账页面。正常重启和断线重连分别检查；未复制日常浏览器资料，也不承诺 Apple 永久免验证。

用户补充当前普通网页仍能登录，因此不能把 503 或 541 直接解释为 IP 被封或中国认证服务全面故障。安装版已恢复 v0.3/0.4 成功时的 Chrome 启动配置，沿用软件原有资料目录；优先比较这个会话与用户的正常窗口。现场确认中国区认证使用 `idmsa.apple.com.cn`，此前识别清单遗漏该域名；现已补齐正常表单识别和失败反馈。

自查的三个验收条件是：错误来自哪一环节、同一软件会话是否实际认证成功、正常重开后是否仍能确认成功。被动诊断仅保存公开主机与固定请求类别，不记录密码、Cookie 或请求正文；界面显示实际运行的浏览器，任务中禁止切换来源。认证服务返回 503 时保留流程，不把辅助资源失败显示为整个商店繁忙，也不反复提交密码。

完整源码检查与安装版自检已通过；原生 Chrome 恢复后的真实登录仍失败，抓到初始化 200、提交 503 / HTML，与内嵌记录一致。日常 Chrome 重新输入密码后的真实成功页面已只读核对，所以继续围绕会话差异排查。iCloud 密码被接受只证明该环节成功，不能代替中国商店认证。真实结果与未解决项见 [登录诊断](LOGIN_DIAGNOSIS.md)，不能以自动化机制检查提前宣布 541 已修好。

## v0.5.1：提前保存账户，登录失败保留当前流程

用户希望无需守着电脑重新输入密码。官网浏览器页新增账户对话框，账号、密码进入独立的 macOS 钥匙串服务，配置只存随机引用；自动登录与信任浏览器提前点选，默认关闭。使用同一持久浏览器，不因掉登录创建新资料目录。修改账户、删除保存密码和完成登录检查均有明确按钮。

产品自查将「Cookie 保存」「密码提交被接受」「Apple 信任浏览器」分为三个验收结果。首次验证码仍需本人完成；之后也不能保证不再验证。成功前不重试同一密码，验证码页保留，身份无法验证单独提示；输入邮箱的取货表单不能触发登录。预约会话检查与结账实际登录表单使用同一能力，保存账户优先于游客备用，登录失败不偷偷改变结账身份。

官方账户帮助页的链接会跳转到 secure7 等节点，节点号不是软件固定的设置，也不能单凭节点号认定 541 的原因。入口改用公开官方链接。软件已修正本地状态判断，但当前网络与 Apple 服务器拒绝的原因仍未确认；真实安装版结果单独记录，不能用离线检查宣称解决 541。

## v0.5.0：先修登录和门店，暂停未经证实的提速方案

用户明确选择继续修登录与门店、暂停代理。双浏览器和多标签页存在响应先后差异，但目前没有 Apple 首发场景的胜出数据；未加入代理部署、自动换 IP、Safari 自动下单或多入口刷新。软件外部调度可避免网页后台定时器降频，服务器是否放行仍不能据此推断。

旧版保存配置时用同一查询地区覆盖所有门店，Duo 无库存入口时也无目录可选。内置官方大陆直营店目录，让选择与库存查询独立；保存每家实际地区，跨城市保留全局优先级，同城不重复查询，旧地区错误按公开门店 ID 修正。

保留软件 Chrome 并增加持久目录的内嵌官网页。加载与明确登录表单分开判断。游客备用由用户提前点选，实际显示入口才执行一次；购物袋保留，短信验证仍需本人完成。立即购买沿用会话，预约购买在开售前复核。

红色关闭按钮在会话打开时隐藏窗口继续运行，明确退出时结束线程、关闭页面再销毁持久资料对象。Qt 退出、会话恢复、门店保存和 Apple 实际认证分别验证；Cookie 重启检查不能代替真实认证。自查和结果见 [发布前自查](PreMortem-iPhone-AutoBuyer-2026-10-12.md) 与 [验证清单](VERIFICATION.md)。

## v0.4.3：先解决意外退出

实际崩溃报告暴露了先前验收的缺口：普通界面自检通过，不代表 macOS 辅助功能读取过表格后仍能安全更新和销毁。三个版本的本机报告均指向 Qt 6.8.3 的辅助功能桥；两个在退出销毁表格时崩溃，一个在切换列表焦点时崩溃。抢购工具应能持续保持登录，稳定性是发布的必要条件。

升级到已包含 Qt 官方 QTBUG-134784 修复的 PySide6 6.11.2；保留辅助功能。退出时先停止计时器、正常结束工作线程及软件浏览器，再在 QApplication 和绑定运行时仍有效时销毁主窗口。新增有数据的表格、辅助功能单元格查询、页面切换和真实工作线程退出回归；最终还要在实际安装版反复操作和重开，结果单独记录。

## v0.4.2：取货信息与入口等待修正

用户填写四位证件却被要求 18 位，原因是自由输入的证件类型触发了另一套校验。取货表单已移除类型输入，按当前官网后四位字段校验；输入完整号码会提示修正，不会静默截取前四位。编辑旧资料只在明确保存时改为后四位，取消不会修改钥匙串。四位数字、末位 X、错误长度和旧资料编辑均有原生表单测试。

复核产品目标：用户应直接填写官网实际需要的取货信息，不承担证件类型与校验策略的配置。后四位足够时不收集完整号码；官网若改变字段要求，需重新核对实际表单。

### 提前同意，满足离开电脑后的运行

用户指出开售时不可能一直守候，并在本次反馈明确要求默认同意、移除二次确认窗口。v0.7.1 默认启用 Apple 中国大陆结账的两个隐私选项，自动勾选并继续。用户可以在付款与授权中关闭，设置重启后保留。

本次调整移除整份正文及版本匹配门槛，保留中国站结账范围及两个隐私选项的识别，不操作其他勾选框。控件未就绪或出现其他选择时显示诊断并保留官网页面，不再创建软件确认弹窗。导入文件仍清除导入的隐私开关；新计划采用用户要求的自动同意默认值。

自查问题：提前选择是否能跨重启使用，是否真的省去开售时点击，是否会误同意新的内容。验收使用保存后重开的原生表单、网络完全拦截的浏览器夹具及最终官网试跑分别记录。按用户最新要求，修改集中完成后再统一验证。

## v0.4.1 历史：入口等待与当次协议点选

固定五分钟等待缺乏 Apple 官方依据，会妨碍首发目标；已改为持续五秒的公开入口节奏、服务器指定等待优先、连续异常才退避。保留队列和未完成导航，不对登录、加购或提交套用 GET 的重试。

早期版本把隐私选择放在当次确认弹窗；该弹窗在 v0.7.1 按用户要求移除，改为默认自动同意。真实网站试跑仍可复用经过完整校验的既有目标购物袋，避免重启检查后要求无意义清空或重复加购。

对原产品审查的复核：入口等待与关键拒绝区分清楚；“刷新失败但有 H1”不能误报进入成功；身份、下单和协议确认仍各有明确的目的与用户动作。离线测试证明控制逻辑，安装版与真实 Apple 流程单独记录在验证清单。

## v0.3.0：恢复真实官网流程，重做原生界面

这轮新增要求是「541 也要解决」和「像 macOS 原生应用」。验收分开：真实官网供货可读、登录可以确认、试跑可到达正确接管点、界面可以看懂并操作。库存读取成功不能代替登录或下单成功。

- **必须：程序能读取在售商品的实际自提信息。** 正式 Chrome 采用受支持本机连接、软件独立资料目录和正常浏览器设置，已由程序读取上海附近 12 家门店；继续验证同一会话重复查询与登录。没有迁移日常浏览器 Cookie，也没有使用隐藏下单 API。
- **必须：等待正常页面状态，不能把错误当成无货。** 配送预估 GET 的 403/541 单独记录；真正库存、登录、订单变更、429 和服务器指定等待仍暂停。自提入口缺失不更新库存时间。供货弹窗的加载骨架要等标题出现后再操作。
- **必须：每次持续检测都取得新响应。** 实际地区选择器记住区县页；重查时先通过可见「省份」标签回到省份选择，随后正常选择目标区县，等浏览器新请求完成才更新时间。调整过的真实浏览器离线夹具先使旧代码失败，修复后通过；官网重复读取另行记录。
- **必须：保持同一软件会话。** 登录、商品、门店和试跑串行共用一个 Chrome 进程。正常关闭使用浏览器自身退出命令保存资料。重启后的有到期时间合成 Cookie 可恢复，Apple 实际认证有效期仍由官网决定。
- **必须：原生界面可以直接使用。** 六页侧栏、细线表单、克制蓝色和白色内容区；控制台集中显示购买计划、时间、登录和日志。已保存的颜色/容量显示中文，内部保留官网原值。默认窗口无裁切；最小窗口允许纵向滚动。
- **保留原有条件：** 单次提交锁、最终商品/总价/数量/门店/付款核对、实际二维码与订单绑定、期限到期隐藏。官网试跑不能自动提交真实订单。

完整视觉稿、实际窗口及逐项比较在 [UI_DESIGN.md](UI_DESIGN.md)。核心源码、打包和官网证据在 [VERIFICATION.md](VERIFICATION.md)。没有把首发尚未发生的拥堵、全品类适配或银行实际付款写成已通过。

| 多地区、配送、多账号等较大功能范围 | 各路径需独立实际验证；当前先完成大陆单账户、自提和付款交接 | 后续评估 |

## 《抢 Duo 的一些关键技术细节》核对

完整阅读用户提供的 13 页 PDF，并检查各页图表。它是第三方实测报告，正文没有给出可复现的完整测试环境、测试日期或请求样本；接口字段、限流阈值和用时均作为诊断线索，不作为 Apple 承诺。第 3 页表格记录的是作者在不同间隔下的观察，不能据此把某个每小时次数设为“保证不受限”的默认值。

| 资料中的线索 | 本机证据与产品决策 | 状态 / 验收条件 |
|---|---|---|
| 模型逐步操作比固定程序慢 | 软件运行由 Playwright 的固定流程执行，不在每一步调用模型；模型只用于开发与本次界面验证 | 已有；阶段日志包含累计耗时，但真实首发速度未测 |
| 首发时页面或接口可能变化 | 官网页面未知必选项、门店或付款信息无法确认时暂停；不把历史私有路径写成跨发售保证 | 已有；发售页变化须用当时页面独立验证 |
| 会话建立、令牌与挑战可能影响加购 | 持续复用同一浏览器；账户命令串行。当前关键请求 HTTP 541 的具体原因仍未知 | 已有；该报告列出的可能原因不能证明本机故障原因 |
| 库存监测与购买分离 | 无货时只重复正常区域供货查询，逐步退避，不创建结账；显示商品配置、检测时间和库存未锁定提示 | 新查询与变化的离线浏览器测试通过；独立软件实际官网查询仍遇 541。单独持续监控入口仍待实现 |
| 短信验证与当次结账绑定 | 现有流程发现可见手机验证控件后暂停人工处理，不反复发送短信。新结账不可沿用旧验证码 | 已有人工路径；自动读取/转发短信未实现 |
| 门店时段由当前结账签发 | 后续增加日期/时段选择时只使用本次可见可选项，提交前核对；失效时段须重新读取 | 待实测；本次已付款后确定取货日期的页面不能用报告的另一条路径替代 |
| 核对页可更改门店而保留其他信息 | 下一轮验证官网“更改零售店”的正常路径，争取保留已完成的取货人、验证和付款设置 | 待实测；变更后重新核对商品、金额、门店与期数，不默认验证仍有效 |
| 订单提交不能重试 | 现有持久订单锁在超时、停止和重启后均保留，只核对结果 | 已实施并通过测试 |
| 付款信息与创建时间可关联 | 现有二维码必须与唯一可见订单号关联；已知提交时刻才计算期限。后续可验证当前页面的创建时间，解决恢复后的未知起算时刻 | 图片裁取已验证；页面模型字段尚未在本机验证，暂不靠重新打开页面延长期限 |

前一天登录与准备购买条件仍有帮助，但 Apple 账户登录、当次结账及短信验证不是同一个有效期。保持打开浏览器不能保证服务器允许旧结账跨天继续；软件在开售前复核，最终按当时官网要求处理。

Apple 官方说明支持将 iPhone 短信同步到自己的 Mac，也说明 Safari 能提供收到的安全码建议（[短信转发](https://support.apple.com/zh-cn/102545)、[Safari 安全码自动填充](https://support.apple.com/zh-cn/guide/safari/ibrwa4a6c6c6/26.0/mac/26)）。这不能证明本软件的独立 Chromium 已有同样能力；本轮不读取“信息”数据库，也没有配置验证码向服务器转发。

报告中的代理池、分布式并发、自动解站点挑战和接码平台没有加入当前单账户产品。本轮保留正常浏览器流程与官网等待要求，不根据资料批量创建订单。

### 独立思考与本机反证

没有直接把 PDF 的“UI 慢”结论改写成“需要重写全部接口”。首先检查正常供货流程是否正确，实际发现两个问题：记住门店后入口叫“Apple 南京东路”；弹窗区域按钮的名称只有“上海”，不是它旁边的说明文字。旧代码分别会等待不存在的入口，或跳过区域动作而读取旧列表。

按 2026-10-11 当前官网控件建立网络完全拦截的浏览器测试，旧实现两个场景均失败；修复后重新查询、无货变有货、拒绝时不发布旧结果、未知控件不更新检测时间均通过。新的查询不调用报告中私有接口，只点击正常区域控件并观察该动作完成的浏览器请求。无货等待也加入逐步退避，避免一直使用初始短间隔。

另外用软件本身正常显示窗口的 Chromium 做两次受控官网读取，只用公开 iPhone 17 配置，不加载身份、不加购、不进入结账。通常准备在 5.90 秒内遇到关键 fetch HTTP 541；等待页面完整加载的对比在进入供货步骤时仍遇 HTTP 541，16.89 秒结束。这个观察说明等待加载未解决拒绝；不能归因于仅使用无头浏览器，也不能依据 PDF 断言是 Cookie 或挑战的哪一个问题。对比还暴露了弹窗等待超时掩盖真实拒绝原因的问题，已修复为优先保留官网限制提示。

## 一页需求：开售前能看懂准备状态，操作失误不会破坏准备

**问题**：v0.1 的关键准备分散在六页；启动失败只提示第一个问题。“停止”关闭预登录浏览器；切换时区只改时区标签会改变实际预约时刻。访问受限后缺少清晰倒计时，多订单只能直接看最近付款码。

**目标用户**：在发售前准备自己或指定取货人的一次购买，开售时减少填表、重登录和错误恢复步骤的人。

**用户流程**：准备检查 → 定位缺失设置 → 官网在售试跑 → 保持软件浏览器登录 → 设定准确开售时刻 → 开售检测 → 官网最终核对 → 订单对应付款码交接。

| ID | 优先级 | 需求与验收条件 |
|---|---|---|
| FR-01 | Must | “停止任务”结束当前操作并保留同一浏览器、会话 Cookie 与进程锁；“关闭会话”或退出应用才关闭浏览器。提交结果不明仍保留订单锁 |
| FR-02 | Must | 时间统一为北京时间；旧时区预约换算并保存后实际时刻不变。过去的预约阻止新真实任务，旧订单仍允许核对 |
| FR-03 | Must | 清单同时列出商品、预算、门店、身份授权、付款、时间、环境、登录和已有订单。每个缺失项可定位设置；官网试跑允许人工填身份，不因此阻塞 |
| FR-04 | Should | 官网受限后显示等待秒数，期限内禁用继续；停止后启动另一个浏览器命令仍须等待，不通过重开任务跳过等待 |
| FR-05 | Should | 门店结果显示检测时间。按商品 URL、配置、数量分开记录变化，相同结果不重复记录。记录只来自实际读取 |
| FR-06 | Should | 可从订单列表选择对应付款码，不把最近付款码当作所选订单的码。重新打开不延长期限；订单列表不把已创建误报为已付款 |
| FR-07 | Must | 活跃任务使用启动时配置副本；界面后续修改不能改变正在执行的购买条件 |
| FR-08 | Must | 通用入口和已记住的门店入口都可识别；查询必须重新触发正常区域动作并等请求和新列表完成。旧 DOM 重读、错误响应和未知控件不能更新检测时间 |
| FR-09 | Should | 无货期间同一浏览器只查询供货，不反复结账；等待逐步增长到配置上限，收到关键拒绝时暂停。弹窗未打开时发生拒绝也保留真实限制原因 |
| FR-10 | Must | 鼠标、macOS 辅助功能和准备清单跳转均保持侧栏选择与实际页面一致，不出现“运行记录”选中但仍显示商品设置的状态 |
| FR-11 | Must | 登录返回还在加载时最多观察 15 秒，显示“暂时无法确认”；关键后台登录请求被拒绝时立即显示 HTTP 原因并保留会话，不自动再次提交密码 |
| FR-12 | Should | 使用紧凑浅色 macOS 工具布局，保留原有六页。默认窗口同时显示预约、登录、状态和日志；减少大卡片、数字导航及装饰文案，诊断功能按需打开 |
| FR-13 | Must | 开售时刷新已准备的目标商品页；公开导航最多等待 8 秒，不等待全部图片。第一次连接失败可正常重试；HTTP 541 的等待不会因导航超时或浏览器错误页被跳过 |

**成功标准**：以上验收场景在本机自动化测试和原生界面中通过；现有单次提交、金额/门店/分期核对及付款码到期保护保持通过。真实首发成功率、24 小时 Apple 登录寿命、桌面自动消费全流程仍待实际验证；测试通过不替代这些结果。

**本轮验证**：v0.2.1 的 105 项已通过。v0.2.2 增加登录异步返回、公开页慢资源、首次连接失败及拒绝期间不刷新验证；最终测试数、安装版和界面证据见 [验证清单](VERIFICATION.md)。

### v0.2.2 的界面与入口判断

用户明确希望界面少一些模板化观感。因此采用灰色侧栏、系统字体、普通按钮和一条紧凑状态栏；当前时钟与阶段不再占用三张大卡片。默认窗口保留足够的日志空间，环境工具与合成数据测试进入「诊断…」。新配置默认北京时间，原有预约时刻与保存设置不作隐式改动。

本机同一天对照发现：普通 Chrome 正常窗口可查到 12 家门店；正式 Chrome 的独立 Playwright 目录仍遇 541，允许正常 Service Worker 也没有恢复。公共网络诊断返回德国，但该服务的路由不能证明 Apple 请求的具体出口。现有证据不足以把故障归为“德国网站”“只有无头模式”或某一个 Cookie；仍须解决独立软件浏览器的实际兼容性。详细时刻、成功与失败的边界见 [入口研究](RESEARCH.md)。
