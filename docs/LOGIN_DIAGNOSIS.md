## v0.6.1：继续改进独立 Chrome 与内置登录

- 官网浏览器页分别提供「内置浏览器登录」与「独立 Chrome 登录」，无需先找控制台下拉框。两个入口使用各自原有资料目录；忙碌中的购买任务不会因切换按钮被改成另一个浏览器。
- 在实际安装版内置浏览器复现了新的入口问题：空购物袋同时显示收藏商品提示中的登录，以及个人资料中的登录，build 21 错将其判为无法选择。随后人工点击个人资料入口，正常进入官网生成的 `/shop/signIn` 页面。这是入口识别问题；没有证明它就是认证提交 503 的原因。
- 核对 Apple 商店当时实际引用的[官方 globalnav 组件](https://store.storeimages.cdn-apple.com/8756/store.apple.com/static-resources/rs-globalelements-2.25.0-4bbf8/dist/ac-globalnav.umd.js)，个人资料链接具有 `gn-bagview-link-signIn` 标记。软件优先选择该唯一官方入口并校验目标域名、协议、端口和路径。没有该标记时只接受唯一链接或完整目标完全相同的重复链接；不同 SSI / 返回上下文继续保留页面。
- 已有账户/订单列表通过同一浏览器的辅助页面重新请求受保护入口确认，原页面保留，不先导航商店或仅凭缓存页面宣称会话有效；已经打开的正常登录/验证页也继续使用。新认证提交 409 或验证成功后解除此前 503 状态，409 本身不算登录成功；必须再确认受保护页面，失败后不会自动重发密码。
- 网络诊断仅查询本机 `scutil --proxy / --nwi / --nc list / --dns`。保存代理开关、代理环境变量的名称、接口类别与数量、标准 VPN 连接数、IP 版本可用性、DNS 服务器集合的摘要；不保存本机地址、DNS 地址、网络名称、VPN 配置名称、代理地址或密码。系统代理/VPN 列表不能完整反映真实公网出口，网络扩展也可能不体现为标准 VPN。
- 系统查询复核发现此前现场脚本误用了 `scutil --nc --list`，返回错误后提取出的 VPN 数量 0 不能当作无连接的证据。已按本机 `scutil --nc help` 改为 `list`，查询失败明确记为 unavailable，并单独用本机查询验证。历史认证请求的 200 / 503 记录与该命令无关。
- 登录期间定期采样，并将认证请求/返回关联至最近的网络观察。通过 [Playwright Response](https://playwright.dev/python/docs/api/class-response) 读取浏览器已收到响应的 HTTP/TLS 版本、对端 IP 版本与地址摘要；不增加 HTTP 请求、不查询第三方出口 IP、不改 VPN、代理、DNS、TLS 或认证域名。采样、传输元数据与结束等待均有时限，不阻塞购买步骤。
- 当前会话保存在本机 `login-diagnostic-chrome.json` 或 `login-diagnostic-embedded.json`；开始下一场会话时将原记录保留到相应 `-previous.json`，每种浏览器最多这两场。文件权限 0600，诊断仍不含请求正文、Cookie、认证头部、账号、密码或响应原文。VPN 中断 Codex 时，本机软件及其采样仍可运行。

最终测试、安装版入口复核和真实认证结果见 [验证清单](VERIFICATION.md)。用户确认的旧版 VPN 成功路径保持为重要线索；新捕获的成功与失败请求链也不能单独确定具体网络因素或服务器规则。

## 早期失败版与后来外部 Chrome 的对照

从本机保留的旧安装包只读提取浏览器模块，核对实际打包代码，而非仅看界面名称。最早保留的 v0.1.0 也采用 Playwright 持久 Chromium；以下对比有实际失败记录的 v0.2.2 与后来成功版本。

| 项目 | v0.2.2 早期失败版 | v0.3.0 / v0.4.0 后来成功版 |
|---|---|---|
| 浏览器启动 | Playwright `launch_persistent_context` 管理 Chromium | 启动本机正式 Google Chrome，再连接 localhost CDP |
| 用户资料 | 软件的 `browser-profile` | 软件的 `chrome-profile`，仍非日常 Chrome 资料 |
| 网页默认设置 | 设置中文、北京时间并阻止 Service Worker | 沿用浏览器默认设置，`connect_over_cdp(no_defaults=True)` |
| 官方账户入口 | `secure.www.apple.com.cn/shop/account/home` | 相同入口，由官网分配安全节点 |
| 真实结果 | 历史认证回调或库存请求 541 | 软件 Chrome 到达双重认证，00:18 UTC 确认登录；v0.4.0 后续复核成功 |

因此“改成外部 Chrome”曾同时改变程序、启动参数、资料目录及网页环境，不能把成功单独归因于外部窗口。当前原生 Chrome 已恢复后来版本的启动方式及同一个软件资料目录；14:24 UTC 与 15:03 UTC 仍在认证提交返回 503。日常 Chrome 当前可重新登录、用户反馈无痕也失败，这支持继续比较会话环境，但没有证明 Apple 的具体拒绝规则。当前记录没有正常成功认证的完整请求链，也没有早期认证响应正文，无法从本机证据确定唯一服务器原因。

## 软件修复

- 预登录从公开商店打开正常购物袋菜单，选择唯一官方个人资料入口；未标记时要求目标唯一。不自行构造 SSI、不复制日常 Chrome 的参数、不调用私有认证 API。已登录时保留会话。后台账户页仍用于只读复核，需要新登录时也改从商店购物袋进入；已有验证页继续保留。
- 同时识别 `/shop/signIn` 与其子路径，拒绝相似前缀、非 HTTPS、其他端口或伪装域名。返回商店时，购物袋记住账户只作线索，沿官网当次账户链接核对受保护页面；过期时保留真实登录页。
- 原生 Chrome 恢复自身资料中的会话 Cookie，同时抑制旧标签页自动载入；现有购买页面在进程重连时保留，正常重启创建新页。没有复制、导出或解密日常 Chrome 的 Cookie。离线复现由失败转为通过；这是掉登录修复，不是首次认证 503 的证明。
- 将实际观察到的 `idmsa.apple.com.cn` 纳入严格认证识别与正常表单登录。仍要求 HTTPS、正常端口及 Apple 中国商店的合法父框架；不扩大到任意 iframe、密码修改页面或其他服务。
- 被动记录正常请求的开始、返回、失败和固定错误类别。只保存固定请求分类、公开主机、HTTP 状态及数字错误码；不保存请求正文、头部、Cookie 或响应原文。区分页面空白时采样与真实 HTTPS 认证框架的能力。
- 认证请求 503 显示服务失败，保留页面和购物袋，不自动再次提交密码。辅助上报资源 503 不再计为商店维护；关键商店 503 仍遵守服务器等待期限。
- 原生 Chrome 启动恢复到 v0.3/0.4 已验证配置：随机非零 localhost 调试端口，继续严格按软件自己的可执行文件、资料目录和用户恢复会话。此前端口 0 的实际浏览器 webdriver 为 true，恢复后的离线浏览器为 false；没有修改该属性，也没有以此宣称官网问题已经解决。
- 显示实际运行与诊断的浏览器，任务中锁定模式选择，避免界面与连接来源混淆。
- 退出检查复现静态定时器及后期创建基础 QTimer 都可能进入 PySide 的空类型元对象；换派生类型和提前释放表格项目均未可靠解决。进一步发现夹具保留了 Qt 已销毁的辅助功能单元格的 Python 包装；夹具改为先释放这些引用再删除行，连续 20 次退出检查通过。应用延迟回调用父窗口持有的 QTimer，保留辅助功能；这个结果不承诺所有 Qt 崩溃都已解决，也与 Apple 网络错误分开验收。

## 尚缺的证据

恢复旧版启动方式和购物袋入口后仍失败，而用户日常 Chrome 的成功页面已现场核对，用户也确认同一软件窗口开启回国 VPN 后成功。503 是失败表现，尚未确定造成它的具体客户端或服务器因素；需要同一会话在两条网络路径下的正常成功与失败认证记录，或 Apple 服务端的明确诊断。新版已经补上本机对照记录，软件不自动切换全局 VPN。没有添加多代理轮换、私有认证接口重放、其他浏览器 Cookie 复制或重复密码提交。

历史 541 发生在供货查询或商店登录回调，当前抓到的 503 发生在认证提交。两者都可能导致前端无法处理正常结果，不能仅因页面症状相似就认定服务端根因相同。
